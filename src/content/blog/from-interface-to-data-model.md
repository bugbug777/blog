我曾參與一個 Web3 社群平台的開發。使用者可以註冊、登入與登出，也能在平台上分享生活日常、心情瑣事，並在內容下方留言。這個專案讓我第一次比較完整地思考，一個網站的前端、後端與 UI/UX 設計是如何彼此牽動。

身為前端開發者，我原本比較熟悉畫面和互動。後端與資料庫則是我不太熟悉的部分，尤其一開始，我不知道資料表或資料集合裡到底該放哪些欄位。要是只憑直覺列欄位，很容易漏掉頁面真正需要的資訊，也不容易看出資料之間的關係。

## 從畫面需要什麼開始

我後來學到一個對我很有幫助的思考方式：先看設計稿和操作流程，列出畫面上要呈現的資訊，再往回推需要哪些資料。

以留言區為例，畫面不只需要留言文字，也需要知道留言由誰發出。每一筆留言可以關聯到一個使用者 ID；顯示留言時，再透過這個 ID 找到同一位使用者的資料，例如名稱或大頭貼。不同使用者可以有不同的大頭貼，讀者便能辨認留言來自誰，畫面也不會只剩下重複的文字區塊。

這讓我理解，資料欄位不是為了把資料庫填滿而存在。每個欄位都應該能對應到功能、畫面或後續操作的需求；資料關聯則讓不同頁面能使用同一份使用者資料，而不必把所有資訊都複製在留言裡。

## 前端與後端如何接起來

在前端，我把後端建立的 API 串接到頁面，把取得的資料整理後呈現在畫面上。這不只是把 API 回傳的 JSON 原封不動放上去，還要理解資料代表什麼、哪些欄位會顯示，以及載入或資料不足時畫面該如何處理。

在後端部分，我也有參與依照設計稿整理資料欄位、設定資料間的關聯，以及規劃 RESTful API。專案使用 MongoDB 儲存資料，前後端透過 JSON 傳遞資料。這些工作讓我開始把 UI/UX 設計、API 和資料模型視為同一個功能的不同面向，而不是互不相干的工作。

## 我如何開始解決資料設計的卡關

真正讓我跨過第一道門檻的，是和有經驗的開發者對話。透過討論，我逐漸知道可以從設計稿裡的元件、文字和互動開始，逐項問自己：這個畫面需要哪些資料？資料由誰建立？它與其他資料有什麼關係？哪些資訊會在多個地方重複使用？

這些問題沒有讓所有設計一次變得簡單，但它們提供了可以開始的方向。當我回頭看留言和使用者的關係時，就能從畫面上的需求推回資料模型，再思考 API 要如何讓前端取得所需資料。

這次經驗讓我明白，資料庫設計不必從抽象的欄位清單開始。對我而言，先理解使用者在頁面上會做什麼、會看到什麼，再從介面需求推演資料欄位與關聯，是一個更容易上手的起點。
